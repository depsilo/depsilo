1.摘要 (TL;DR)

两个独立结论,互不依赖,可以分别决策、分别落地。

代码层面

整体健康度高 — 13 个 adapter 模式统一、缓存核心成熟、依赖注入清晰。没有"灾难性"债务,但有一组围绕 "按生态分散 12 个独立字段" 的重复模式,在 Deps / NewStatsHandler / NewDashboardHandler / 配置 / Pool 注册之间反复出现,合计影响约 8 个文件,每次新增生态都要改这 8 处。这是唯一值得专门立 ADR 的重构。其余项基本是"看到即可顺手清理"的低风险整理。

功能分层

当前的 Pro 边界(audit / rules / security / projects)整体合理,但有两个隐患:

  • 跟竞品同质化。Pro 矩阵几乎完全对标 Nexus/Artifactory,缺少差异化抓手 — SBOM 这种独有能力反而被埋在 Pro 内部没被叫卖。
  • 没有 Enterprise 抓手。LDAP/SSO/集群/Webhook 这些大客户必需品,既不在 Free 也不在 Pro,目前是"灰色待定"状态 — 未来要么挤进 Pro 拉高定价,要么作为 Enterprise SKU 独立存在。建议明确为后者。

由于 Buyer 数据缺位,本报告不下唯一定价结论,而是给出三个 Buyer 动机假设(合规 / 安全 / 治理)下的功能归属矩阵,以及两周内能消除不确定性的验证清单。

2.3关键重构机会(展开)

2.3.1   按生态分散的 12 字段 → map[string]*Pool 高

现状:每新加一个 ecosystem,都要在以下位置同步修改:

  1. internal/config/config.go — 增 Ecosystem config.UpstreamGroup
  2. internal/server/server.go:99-117 — ecosystemDef 表加一行(已表驱动)
  3. internal/api/router.go:26-50 — Deps.XPool *upstream.Pool 加一个字段
  4. internal/api/router.go:60 — NewStatsHandler(...) 传参加一个
  5. internal/api/router.go:94 — NewDashboardHandler(...) 传参加一个
  6. internal/api/public/stats.go:19-56 — struct 字段、构造函数、stats 输出 3 处加
  7. internal/api/admin/dashboard.go:18-33 — 类似 stats.go
  8. internal/api/router.go:110-116 — warmupPools map 已经是 map 但是手写

目标结构:

// internal/api/router.go
type Deps struct {
    DB             *gorm.DB
    Storage        cache.Storage
    Config         *config.Config
    Pools          map[string]*upstream.Pool  // ← key 即 ecosystem name
    CacheMgr       *cache.Manager
    EventBus       *cache.EventBus
    LicenseManager *license.Manager
    AuditLogger    *audit.Logger
    RulesStore     *rules.Store
    RulesEngine    *rules.Engine
    SecurityScanner  *security.Scanner
    SecurityImporter *security.Importer
}

// internal/api/public/stats.go
type StatsHandler struct {
    db    *gorm.DB
    storage cache.Storage
    pools map[string]*upstream.Pool   // ← 单字段,代替 12 字段
    startTime time.Time
    extraIndexes []config.ExtraIndexConfig
}

func NewStatsHandler(db *gorm.DB, storage cache.Storage,
                     pools map[string]*upstream.Pool,
                     extraIndexes []config.ExtraIndexConfig) *StatsHandler {
    return &StatsHandler{db: db, storage: storage, pools: pools,
                          startTime: time.Now(), extraIndexes: extraIndexes}
}

迁移步骤(每步独立,可分多次 PR):

  1. 给 Deps 加 Pools map[string]*Pool 字段,不删旧字段。server.go 同时填两份。
  2. 把 NewStatsHandler、NewDashboardHandler 改成接 map,同时保留旧入口名(用 deprecation 注释)。
  3. 调用方一次性切到新签名,删旧字段。
  4. 跑全套测试 + Docker E2E。

风险:

  • stats / dashboard handler 内部对每个 pool 都有"如果该生态没配置就跳过"的判断,迁移时要确保 pools[name] == nil 的语义与旧代码"空字段"一致。
  • 测试覆盖目前在每个生态级别,集成测试是稳定锚。

预估:1 个 PR / 0.5–1 工作日,影响 ~8 文件,~200 行 churn。

推荐落地形式:专门立一个 ADR,因为这是"为下一个生态预先扫清路径"的决策,值得记录。

2.3.2   cache/manager.go 内的 package-key 解析剥离 高

现状:cache/manager.go 681 行的实际功能分布是:

区段函数行数类型
L1–37imports + countingReader~37缓存核心
L39–211ExtractPackageName~173adapter 元数据,不属于这里
L213–353ExtractPackageVersion~141adapter 元数据,不属于这里

"缓存核心"只占 305 行;包名/版本提取占 352 行 — 整个文件的一半其实是 adapter 元数据,被错放在了 cache 包。

目标结构:

internal/
├── cache/
│   └── manager.go              # ← 缩到 ~310 行,纯粹做缓存编排
└── adapter/
    └── packagekey/
        ├── extract.go          # ExtractPackageName / ExtractPackageVersion
        ├── classify.go         # IsPackageFile
        └── extract_test.go     # 单元测试

动机:

  • cache 包不应该知道什么是 "wheel" / ".deb" / ".gem" — 这些是 adapter 知识。
  • 新增一个生态时,改 cache/manager.go 是反直觉的;改 adapter/packagekey/ 更自然。
  • 这两个函数被 access_log 写入和 stats 聚合调用,与 manager 状态无关,迁移零风险。

预估:1 个 PR / 半个工作日,~3 文件 churn。

风险:无。纯文件搬运 + import 调整。

2.3.3   13 个 adapter handler 抽出共享脚手架 中

现状:13 个 handler 都符合下面这个流程:

1. 从 gin.Context 解析路径 → 生成 cache key
2. 决定 TTL(短 TTL for 元数据,长 TTL for 包文件)
3. 调用 cacheMgr.Get(ctx, key, ttl, fetchFn)
   ↳ fetchFn 内部:从 pool.Select() 拿上游,组装请求,发出去
4. (可选)重写响应体里的 URL
5. 把 response 流式写回客户端

差异点只有三处:(a) key 怎么算(keyer.go 已经独立)、(b) TTL 怎么挑、(c) 是否需要响应重写。

目标结构:

// internal/adapter/base/handler.go (新)
type Server struct {
    Pool     *upstream.Pool
    CacheMgr *cache.Manager
    Type     string  // adapter type
}

type Request struct {
    Key      string
    TTL      time.Duration
    Upstream string  // 上游 path
    Rewriter func(body []byte) ([]byte, error)  // nil = passthrough
}

func (s *Server) Serve(c *gin.Context, r Request) {
    // 单飞 + 选上游 + 缓存 + 流式响应
    // 13 个 adapter 不再重复这套
}

具体 adapter 退化为:

// internal/adapter/maven/handler.go (~30 行)
func (h *Handler) handleRequest(c *gin.Context) {
    path := c.Param("path")
    h.server.Serve(c, base.Request{
        Key:      keyer.Key(path),
        TTL:      keyer.TTL(path),  // SNAPSHOT 短,release 长
        Upstream: path,
    })
}

风险:

  • PyPI / Cargo / Docker 有特殊语义(HTML 解析、URL 重写、token 认证),不能强塞到 base 里 — 它们应该退化为"用 base 跑大部分流程,关键步骤注入自己的回调"。
  • 这种抽象很容易抽错(DRY vs Premature Abstraction)。建议先做 2.3.1 和 2.3.2,等三个月再回头看是否值得做这个。

预估:2–3 个 PR / 3–5 工作日,~14 文件 churn。

是否推荐立即做:不。等下一个新生态需求出现时再做(届时收益和风险都更清楚)。

3.功能分层(情景化矩阵)

前置免责声明

本节所有结论建立在未经 Buyer 验证的假设之上。Operator 画像(国内 50–300 人科技公司的 DevOps 工程师)已经在访谈中确认,但 Buyer 动机(为什么签字付钱)没有真实数据撑腰。

因此本节产出的不是"X 应该放 Pro / Y 应该放 Free"的唯一结论,而是三种 Buyer 动机假设下的功能归属矩阵,以及末尾的 两周验证清单 — 跑完清单后,这张矩阵会自动塌缩到一个具体方案。

3.1当前 Free / Pro 边界(现状描述)

从 internal/api/router.go:160-196 中 license.RequirePro 包围的路由直接读出:

层级功能模块API 路径
Free 13 个生态代理(pypi/apt/npm/go/cargo/maven/rubygems/composer/nuget/conda/cran/helm/docker)、缓存引擎(SWR + 单飞 + LRU)、本地/S3 存储、Portal(QuickStart + Monitor + Packages + LiveStream + SetupWizard)、Admin(Dashboard + Bandwidth + Cache + Upstreams + Logs + Users + Tokens + Settings)、JWT 认证、Prometheus metrics、SSE 实时流 除下方外的所有路由
Pro 审计日志(Audit Log) /api/v1/admin/audit-logs(/export)
Pro 规则引擎(Rules) /api/v1/admin/rules
Pro 安全情报(Security / OSV / Policies) /api/v1/admin/security/*
Pro 项目管理 + SBOM 导出 /api/v1/admin/projects/* + /projects/:id/sbom
Enterprise
(尚未存在)		 LDAP / SSO、集群、Webhook、SLA 支持 无

这套划分跟竞品 Nexus/Artifactory 的 Pro SKU 几乎完全对标。问题是:

  1. 没有差异化抓手。"Depsilo Pro 给我的东西竞品也给"。SBOM 是少数差异化点,但目前埋在 Pro 内部没被叫卖。
  2. 没有 Enterprise 层级。LDAP/集群/Webhook 这三个 — functional-analysis.md §3.1 已识别为缺口 — 目前不知道该挤进 Pro(拉高定价赶走中小客户)还是单独立第三档(增加产品矩阵复杂度)。
  3. 免费版可能"太慷慨"。完整 Bandwidth Report、SetupWizard、LiveStream(SSE 实时流) — 这些在某些 Buyer 眼里是"我愿意为之付费的差异化体验",目前白送。

3.2三个 Buyer 动机假设

同一个 Operator 小李,他的老板可能因为三种完全不同的原因签字付 Pro。每个假设导出不同的分层方案。

H1 · 合规驱动 假设

Buyer 痛点:过等保 2.0 / ISO 27001 / 软件供应链审计,审计师要 SBOM、要"谁批准了这个包"、要"漏洞修复证据"。

购买触发:监管文件下达 / 审计倒计时 / 合规咨询机构推荐。

Pro 主 SKU = 合规包(SBOM + Audit Log + OSV 报告)。

代码契合度:高(SBOM、OSV、Audit 都已实现)。

H2 · 安全驱动 假设

Buyer 痛点:供应链投毒事件吓到(event-stream / colors.js / xz)。"我们用没用这个包?能不能阻止它进来?"

购买触发:新闻爆出 → 老板拍桌子。

Pro 主 SKU = 安全包(Rules 阻断 + OSV 扫描 + 实时告警 + Webhook)。

代码契合度:中(Rules + OSV 有,但缺实时告警和 Webhook,要补)。

H3 · 治理驱动 假设

Buyer 痛点:团队从 3 个长到 8 个,谁动了什么没人说得清,A 组的改动挂了 B 组的 CI,需要"分项目、分人、可追溯"。

购买触发:一次跨团队事故。

Pro 主 SKU = 治理包(Projects + 项目级 Token + Audit + 配额)。

代码契合度:中(Projects 有,但缺项目级配额、跨项目报告)。

矩阵阅读说明

三个假设差异最大的三个判断点:

  1. Bandwidth Report 是否 Free:H1/H2 倾向 Free(对 Buyer 没说服力),H3 倾向 Pro(给老板看"省了多少钱"是治理 ROI 证据)。
  2. 审计日志是否 Free:H2 下可以下放(看历史不直接抵抗供应链投毒),H1/H3 必须 Pro。
  3. Webhook 是否必要:H2 必补(否则"实时阻断"故事不成立),H1/H3 nice-to-have。

三个假设共同的判断:

  • 13 生态代理 + 缓存核心 + 基础 Dashboard 永远 Free。
  • SBOM + OSV + Rules + Projects 永远 Pro(代码已经这么做了,各假设下都成立)。
  • LDAP/集群/SLA 永远 Enterprise。

3.4Enterprise 第三档建议

不管最终走哪个 Buyer 假设,建议立第三档 Enterprise。理由:

  1. LDAP/集群/Webhook 这三项是大客户进门必问的,但如果挤进 Pro,会把 Pro 定价拉高到中小客户买不起;留在 Free 不可能(开发量大且不影响小团队);独立成 Enterprise 是唯一合理位置。
  2. Enterprise 是销售触发型而非产品触发型。Pro 可以走自助网站下单(license key 模式 — 代码已支持),Enterprise 走 inbound 询单 + 定制报价。两种销售模式分开,不互相干扰。
  3. Enterprise 不需要现在就把功能做出来。先在官网定价页留位置("Enterprise · 联系我们"),收 inbound 询单,有真实客户后再做。这是 Cunningham 的 "Build Service Then Product" 路径。

3.5两周内 Buyer 验证清单

用以下 4 步把"三个假设"塌缩到一个具体方向。每步独立,做完一步就有信息。

第 1 步 · 自己先选默认锚(本周内)

在 H1/H2/H3 三个假设里选一个作为"我心里押宝的方向",先不公开宣称。挑选标准:

  • 读完 §3.2,你"心动"程度最高的那个 — 这通常是你潜意识在偏好的。
  • 查代码契合度:H1 最高(SBOM/OSV/Audit 都已实现);H2/H3 中(各缺一个关键能力)。
  • 读 CLAUDE.md §11.4 已写"SBOM 是独有能力" — 这是 H1 的另一个隐含证据。

推荐默认锚:H1(合规驱动)。但下一步必须用真实对话验证它,不能只靠"代码已经走这条路"就拍板。

第 2 步 · 5 通真实电话(下周内)

找 5 个潜在 Buyer 画像的人聊一次,每次 20 分钟。不要演示产品,只问问题。

来源建议:

  • 个人/前同事网络:认识的 DevOps 负责人、技术总监、安全负责人 → 各 1–2 个
  • 开源社区:Hacker News / V2EX / 即刻 / X 上发"做了个开源依赖代理,想找用过 Nexus 的朋友聊 20 分钟,送早咖啡"
  • LinkedIn:搜"DevOps Manager"/"基础架构负责人",冷邮件投 20 个,通常回 3–5 个

问题清单(不要问"你会买 Depsilo Pro 吗",问 desperate specificity 问题):

  1. 过去 6 个月里,因为包管理/依赖问题,你最具体的一次麻烦是什么?(听他讲故事,不打断)
  2. 这件事最后怎么解决的?谁花了多少时间?
  3. 如果再发生一次,你愿意花什么样的钱避免?(注意:他主动说出"年订阅"还是"一次性买断"还是"免费就行")
  4. 你们今年/明年有没有合规审计?(如果有 → H1 信号;如果他说"完全不关心" → H1 弱)
  5. 过去 1 年里,你或你老板有没有因为"某 npm/PyPI 包出事"被叫去解释?(如果有 → H2 信号)
  6. 你们公司有几个团队在用同一套依赖源?各自独立还是混着用?(如果≥3 个且彼此干扰 → H3 信号)

第 3 步 · 给"假装定价页"看反应(同步进行)

不要真上线 — 做一个静态 HTML 定价页(Free / Pro / Enterprise 三档,Pro 标 ¥1,500/年/实例 或类似数字),仅在邮件签名 / GitHub README / 私下私信里露出。看哪一档收到的"询问邮件"最多。

记录维度:

  • 哪类用户(规模 / 行业 / 角色)在问哪一档
  • 询问内容偏向(合规 → H1 / 安全 → H2 / 多团队 → H3)
  • 价格弹性反应(觉得太贵 / 觉得合理 / 主动问折扣)

第 4 步 · 塌缩矩阵(两周末)

把第 2、3 步的真实数据填回 §3.3 矩阵:

  • 如果 ≥3 通电话指向 H1 → 锁定 H1 列,删 H2/H3,Pro SKU 主打"合规包"
  • 如果指向分散 → Pro 用三个假设的"共同 Pro"作为最小集,H1/H2/H3 差异项留 Enterprise 或后续迭代
  • 如果完全没人愿意付钱 → 严肃考虑取消 Pro,走 sponsorware / dual license / 卖支持路径(这是个独立报告,不在本范围)

两周清单(可直接打印)

  • 本周内 — 自己挑一个默认锚(推荐 H1),写在便签上,不公开
  • 本周内 — 拟 5 封冷邮件 / DM,定 5 通电话时间
  • 下周完成 5 通电话,每通 20 分钟,只问不卖
  • 下周内 — 做静态定价页,挂 README + 邮件签名
  • 两周末 — 整理 5 份电话笔记 + 询问邮件,塌缩矩阵
  • 两周末 — 决定:走哪个 H,Pro 主 SKU 是什么,Enterprise 抓手是什么
  • 下个月 — 上 Pro 销售页(基于已验证的 H),开始收第一笔 Pro 订单
