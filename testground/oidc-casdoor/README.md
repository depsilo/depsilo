# Isolated Casdoor OIDC fixture

This opt-in fixture runs a real Casdoor identity provider on the local Docker
engine. The provider helper does not change an existing Depsilo instance. The optional
`depsilo-smoke.mjs` integration below starts its own disposable Depsilo process.
The remote `mcs` service is not involved.

## Start, inspect, stop

Requirements: Python 3 and local Docker with Compose. Browser tests additionally
use the repository's locked `web/node_modules` and Playwright Chromium. No new
application dependency is needed. The first start pulls the pinned image and
therefore requires registry access.

From the repository root:

```bash
python3 testground/oidc-casdoor/fixture.py start
python3 testground/oidc-casdoor/fixture.py status
python3 testground/oidc-casdoor/fixture.py metadata
python3 testground/oidc-casdoor/fixture.py paths
python3 testground/oidc-casdoor/fixture.py stop
```

With the fixture running, execute the real browser/protocol probe:

```bash
node testground/oidc-casdoor/browser-smoke.mjs
```

It temporarily listens on `127.0.0.1:18082`, launches the existing Playwright
Chromium installation, and closes that listener/browser when done. It keeps
Casdoor running. The sanitized result is written to
`~/.cache/depsilo/oidc-casdoor/evidence/browser-smoke.json`; the initial login
page screenshot is `evidence/casdoor-login.png`. A successful probe proves this
provider configuration, not Depsilo SSO, application authorization, or directory
synchronization. The helper is an integration test, not production OIDC code.

The independent Compose project is `depsilo-oidc-casdoor`. Its only published
port is `127.0.0.1:18000`. The script rejects remote Docker contexts and
`DOCKER_HOST` overrides. It deliberately has no reset/delete-data command.
`stop` removes this project's container/network while preserving private state;
`start` reopens the same database and keeps credentials and external subjects.
It leaves the service running after checks.

Open **http://127.0.0.1:18000**. The Casdoor console uses the generated
`console` credentials, rather than a public default password. `paths` reports
the credential file location without printing its contents:

```text
~/.cache/depsilo/oidc-casdoor/credentials.json
```

The directory has mode `0700`; generated credential, seed and config files have
mode `0600`. The directory also contains SQLite, its WAL files, private server
logs, metadata snapshots, and test evidence. Keep it outside Git. Treat browser
traces and HTTP logs as sensitive: authorization codes and tokens may appear in
them. Do not attach the private seed, credentials, database or raw traces to PRs.

The Depsilo callback is registered for the optional application integration;
`fixture.py start` starts only the identity provider. Use the exact issuer and redirect URI, not
`localhost` aliases. HTTP is intentional for this loopback-only fixture; a
remote integration needs HTTPS and an origin reachable from both browser and
backend.

The fixture sets the SQLite DSN explicitly in Compose. The all-in-one image's
entrypoint exports a default DSN when its environment does not contain one,
which otherwise overrides `app.conf` and places the database inside the
container. Its database must instead live at `/fixture/casdoor.db`.

Signing keys are generated by Casdoor when importing a dedicated empty test
certificate record. Passwords, the client secret, and the console bootstrap
password are generated locally on first start. `initDataNewOnly=true` prevents
restarts from overwriting changes to existing fixture users. The built-in
console organization is separate from the single application organization.

## Test identities

| Username | Casdoor group | Intended downstream mapping | Identity state |
| --- | --- | --- | --- |
| `admin-test` | `depsilo-test/depsilo-admins` | Depsilo administrator | Enabled |
| `reader-test` | `depsilo-test/depsilo-readers` | Depsilo readonly | Enabled |
| `unmapped-test` | `depsilo-test/unmapped` | Deny application access | Enabled |
| `disabled-test` | `depsilo-test/depsilo-readers` | No login | Forbidden |

The integration runner applies these mappings only to its disposable Depsilo. None of
these users is a Casdoor organization/global administrator. An enabled unmapped
user may authenticate successfully at Casdoor; a relying party must then deny
entry according to its own explicit mapping. The disabled user must be rejected
by the provider itself.

The private JSON has `issuer`, `organization`, `application`, `client_id`,
`client_secret`, `redirect_uris`, a `console` object, and `users` keyed by the
usernames above. A probe should read the file directly and print only sanitized
results. User entries contain `username`, `password`, `groups`, and `forbidden`.

## What to validate

`metadata` checks exact issuer equality, S256 advertisement, expected endpoint
origins, and non-empty global/application JWKS. It stores the provider metadata
and public signing keys in the private `metadata.json` evidence file. This is
endpoint validation, not proof of a successful user login.

The browser/protocol test should actually authenticate with Casdoor, perform
Authorization Code + S256 PKCE, verify the ID token signature/issuer/audience/
expiry/nonce, then compare UserInfo `sub` with the ID token. `JWT-Standard`
groups need the `profile` scope and a UserInfo call. Verify the expected groups,
an unmapped identity, a forbidden identity, and invalid PKCE without turning off
any protocol validation. Use fresh browser contexts and a fresh transaction for
each login. Do not write tokens or authorization URLs into public test output.

The broader scope and remaining integration questions are recorded in
[the Casdoor research note](../../docs/research/2026-10-22-casdoor-oidc.md).

## Recorded validation (2026-10-22)

On local macOS/OrbStack with linux/arm64 Casdoor, the real browser probe passed
six scenarios: enabled administrator-group, readonly-group and unmapped-group
users completed Authorization Code + S256 PKCE with signature, issuer, audience,
nonce and UserInfo subject/group checks; a consumed authorization code and an
incorrect PKCE verifier were rejected; the forbidden user could not sign in.
The probe's role labels are assertions in the test helper, not Depsilo policy.

The fixture was stopped (container and project network removed) and started
again. User subjects, forbidden state, signing key and credentials were
unchanged. The same six browser scenarios passed again after that restart.
The private `evidence/lifecycle.json` records the persistence checks.
Metadata transport checks also confirmed that a configured HTTP proxy is
ignored and a redirect response is rejected.

The future Depsilo callback was aligned with its `/api/v1` prefix in the seed,
private credentials and the running test application's allowlist. This exact
test-application change preserved user subjects, signing key and client secret;
the standalone probe callback was unchanged. Its record is
`evidence/callback-update.json`.

Not exercised by the provider-only probe: Depsilo login/session/authorization, existing enterprise identity
configuration, MFA, provider logout/back-channel revocation, API Token lifecycle,
amd64 runtime, external HTTPS/reverse proxy, or provisioning synchronization.


## Real Depsilo integration

With Casdoor running and locked frontend dependencies installed:

```bash
make build
node testground/oidc-casdoor/depsilo-smoke.mjs
```

The runner refuses an occupied port 18081, creates a private run directory under
`~/.cache/depsilo/oidc-casdoor/runs/`, bootstraps a separate SQLite instance with a
random local administrator password, and starts the built application bound to
loopback. It passes the client secret through the child process environment.
No normal local or remote instance configuration is changed. Its Depsilo process
and browser stop afterward; Casdoor and private evidence are retained.

The Chromium flow tests real application linking, external sign-in to the same
local account, unlink revocation while retaining password recovery, managed-user
explicit account creation and role mapping, absolute refresh limits, logout revocation, readonly write
rejection, unmapped denial, and local disable surviving a provider re-login.
It first creates an additional disabled OIDC source through the protocol-based
source editor, checks independent configuration and unchanged login availability,
and removes that unused draft. A real discovery/JWKS check and isolated browser trial verify the mapped role
without creating account, binding or session rows or replacing the local token.
The runner also checks that an unassociated login creates no account before an
explicit choice: cancellation creates nothing, a fresh local password proof
binds the existing account, and explicit creation yields a separate managed
account. It then edits the compatibility source (`oidc`)
through the source-specific system authentication form, saves a 20-minute session limit,
checks that the running 30-minute limit remains unchanged until restart, and
restarts only its disposable Depsilo process. After restart it verifies the new
limit, revocation of a previously valid external session, and preservation of
local recovery. It then changes only the source display name, verifies the
pending save reports no session reset, and restarts the disposable process.
The same external JWT must still work for the same account and authority while
public login and account-binding labels update. A subsequent session-limit
change must report a pending session reset and revoke that same JWT after
restart, while leaving the local recovery token valid. This reuses the existing
external session without additional provider logins.
Environment-provided secrets must remain absent from both API
responses and the saved configuration. Actual account pages at desktop/mobile
sizes and system authentication pages before/after restart are captured. No API
mocks are used. Deliberate one-minute pauses respect the production login rate limit.
The final stdout contains sanitized results and the evidence directory; tokens,
passwords and raw provider errors are never printed. On failure, the exception
stack is retained only in the private run directory as `failure.txt`; it may
contain browser or protocol details and must not be shared unredacted.

The separate provider probe covers forbidden Casdoor users and PKCE/code replay;
Go tests cover protocol corruption, competing bindings and callback state expiry.
Neither probe certifies another identity provider, remote HTTPS/reverse proxies,
MFA policy, global IdP logout, SCIM or back-channel revocation.


The application runner passed all seven scenario groups on 2026-10-22 against
the production build and the pinned Casdoor fixture, including preservation of
encoded query/fragment return destinations. The account screenshots are real
application pages from an isolated test instance, not production user data.
The repository-wide offline gate also passed (403 browser cases, one skipped).
The security scan still reports existing baseline findings; adding OIDC did not
add a called Go vulnerability ID or change the frontend dependency lockfile.


On 2026-10-23, the updated multi-source application passed all ten runner
scenario groups against the unchanged Casdoor fixture. This included creating
and removing an independent disabled OIDC source, editing the legacy `oidc`
source through the new source-specific API, and verifying its saved settings
after restart. The running provider remained the single existing Casdoor
instance; concurrent active-source isolation is covered separately by the Go
tests with independent HTTP identity providers.


The subsequent account-choice and diagnostic iteration on 2026-10-23 passed
all twelve application scenario groups against the same preserved Casdoor
fixture. Real discovery/JWKS and browser trial succeeded without creating
users, bindings or identity sessions and without replacing the local admin
JWT. A first unassociated login left all three tables unchanged until an
explicit choice; cancellation kept them unchanged, local password proof linked
the existing account, and explicit creation produced a managed account. The
original binding, unlink revocation, role, refresh, logout, disable and restart
checks also passed. Trial and first-login-choice screenshots are included in
the private run evidence alongside the existing desktop/mobile account views.
